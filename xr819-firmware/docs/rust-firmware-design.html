XR819 open firmware: architecture review and work plan

Revision 8. Rebuilt from the current source tree, current README, the 2026-08-15 handoff, the TX ownership documents, and DTCM appendices A.105–A.121. Revision 8 moves DTCM runtime-contract closure ahead of source decomposition and moves HIF publication-contract proof ahead of additional hardware TX concurrency. The goal is clean, idiomatic, performant Rust firmware that replaces the vendor binary. Vendor code and layouts are evidence about hardware contracts, not a requirement to reproduce vendor internals.

1. Executive summary

The project is already a functioning firmware, not an early bring-up scaffold. The hif-startup image completes Linux probe, scans actively, joins WPA2, completes the four-way handshake, encrypts protected traffic with the XR819 AES engine, and carries sustained TCP/UDP. The qualified image 88298e82… passed three fresh boots at 4.87–5.09 Mbit/s TCP and 7.92–7.93 Mbit/s UDP with 20/20 final ping and zero exceptions.

The correct near-term strategy is therefore consolidation and measured extension: preserve the working cooperative execution model and ownership rules, make their implementation smaller and more explicit, close security and lifecycle gaps, then add safe hardware concurrency and aggregation. DTCM address retirement is a separate long-term closure project. It must not be mixed into ordinary refactors or throughput work.

Recommended order: establish the live DTCM initialization/access contract, perform behavior-preserving reactor and TX decomposition, close correctness and security gaps, prove the HIF publication contract, qualify recovery, add measured per-pipe TX concurrency, add A-MPDU, then retire the DTCM ABI atomically after all fixed-address writers are gone.

2.3 Actual open production items

  • Active-VIF channel restoration and complete power-save resumption.
  • CCMP replay protection.
  • Controlled degraded-RF fallback and long-duration soak qualification.
  • Production recovery policy for architected CPU exceptions and unrecoverable packet-controller faults.
  • A-MPDU aggregation and, before it, ownership-safe multiple hardware-owned frames or per-pipe credits.
  • Complete HIF publication semantics as a design choice: exact vendor request-buffer lifetime is not required, but the chosen copy/credit/queue contract must be explicit and pressure-safe.
  • Final DTCM ABI retirement after whole state-machine closures become native.

3. Architecture that should be preserved

3.1 Cooperative reactor, not a new RTOS

The main loop already has independent service lanes and bounded work. This is appropriate for the ARM9-class single-core target and is proven on hardware. A new RTIC-like scheduler would add priority-ceiling machinery and interrupt-latency risk without solving a current defect.

packet-DMA/HIF IRQ service
  -> pipe watchdog
  -> retained host-TX service
  -> management TX completion
  -> command/confirm/debug publication
  -> scan and probe service
  -> RX indication or idle recycling
  -> exactly one host request dispatch
  -> repeat

The invariant to preserve is that a pending or stuck data frame never gates synchronous command progress. Management and class-0 share the MAC runtime, but the host command lane remains independent.

3.2 Host-TX ownership

The pure model and runtime use the following concepts:

HardwareOwnership = Reversible | HardwareOwned
Stage = Free | Retained | Pending | PasQueued | Reserved | Scheduled | ConfirmationReady

irreversible boundary = scheduler publication / hardware GO
completion identity   = (context, frame_node, pipe, slot)
  • A detached HIF request has exactly one owner and its release token is consumed exactly once.
  • A hardware-owned context cannot be cancelled, freed, or reused.
  • Completion is identity-based, not FIFO-based and not selected by packet-id order.
  • At most one class-0 owner currently reserves or owns the shared MAC runtime.
  • Rejected designs remain rejected: no FIFO above HostTxDriver, no withholding HIF requests while TX is active, and no artificial busy failure for ordinary bursts.

host_tx_arena.rs is currently a pure model while HostTxDriver contains the target runtime states. Keep the model as an executable specification, but avoid growing two independent state machines. Shared transition decisions should move into host-testable functions used by both.

3.3 MAC exclusion and volatile access

Do not add a second generic interrupt guard. MacDomain and MacDomainGuard already provide the correct capability for multiword scheduler, pending-list, PAS, pipe, and completion transitions. Extend their use where audits find an unguarded shared invariant.

  • Volatile is representation access, not synchronization. DTCM state shared with IRQ/FIQ uses volatile loads/stores and a domain guard for compound transitions.
  • Rust atomics are not a device-memory coherence mechanism. Use compiler fences, CPSR exclusion, and the existing write-buffer drain or hardware barrier at publication points.
  • Do not form safe references to quarantine records. The fixed layout remains UnsafeCell<MaybeUninit<...>> with field-derived raw volatile access.
  • Packet RAM, HIF SRAM, MMIO, DTCM, ITCM state, and stacks remain distinct address and ownership domains.

3.4 DTCM is a quarantine ABI, not the desired state store

The implemented DtcmLayout remains the complete 0xa000-byte host layout oracle. ARM allocation is now partitioned by startup contract into exact contiguous .dtcm.data, .dtcm.bss, and .dtcm.noinit sections. This prevents accidental hole allocation, preserves overlays, and lets checkers verify boundaries. It does not prove exclusive Rust ownership and it is not movable. The accurate claim is that DTCM is structurally decoded, link placed, and quarantined, not that its usage is fully translated.

Current contract gap: all three DTCM sections remain NOLOAD and the packed-image checker rejects DTCM COPY/FILL records. .dtcm.data still receives the qualified vendor COPY image, .dtcm.bss still uses explicit startup zeroing, and .dtcm.noinit retains the research margin. Direct production DTCM literals are eliminated outside src/dtcm.rs, and direct arithmetic on a dtcm::...get() expression is blocked. Older family-local aliases and record-internal arithmetic still require audit. The boot/retention source and cold/warm snapshot behavior of every live initialized word must be closed before ordinary source decomposition can be called safe. The active writer matrix and capture procedure are maintained in dtcm-runtime-contract.md.

The internal TX context pool, 30-record host TX context array, host-context accounting/free-list roots, link/sequence state, join/scan and WSM response state, BA/LMC/session/link state, TALA accounting, and completion prefix are the first runtime families migrated from the opaque BSS allocation. Opaque and typed input objects are linked contiguously into the same .dtcm.bss output section. The host contexts have a regular Rust allocation identity at 0x04005a24..0x04008544, their accounting/free-list roots occupy 0x04008798..0x040087b8, link, sequence, and aggregate-member state occupies 0x040087b8..0x040089d8, join/scan, WSM response, and BA/LMC state fills 0x040089d8..0x04008e78, BA/TALA/completion state occupies 0x04008e78..0x04008f80, and the internal pool retains its exact 0x04009080..0x040094d4 hardware ABI.

  • Ordinary translated CPU-only state already belongs in ITCM .data/.bss. Do not move it back into DTCM for visual symmetry.
  • The exact three-section partition is the allocation authority. New typed family statics replace reviewed subranges within that partition; they must not overlap, create holes, or silently split ownership before family closure.
  • Address movement is allowed only after every reader, writer, callback, IRQ/FIQ path, computed root, and high-TCM consumer for the family is retired.
  • The final relocation/removal is atomic. The failed TALA move proves that exact struct shape and source arithmetic do not establish address independence.

4. Corrections to the previous hosted plan

Previous claimCorrection
Hardware AES was a future optimization; RustCrypto was the target backend. False. ARM target builds use the XR819 AES engine today. RustCrypto is used on the host and as an independent correctness oracle.
IRQ 18/20/21 completion translation was future work. IRQ 18/20 hardware crypto callbacks are implemented and registered. The vendor MIC-21 path is not a required backlog item for the current hardware-CCMP design.
A new IrqGuard and generic Cell<T> layer should be introduced. MacDomainGuard already implements the relevant CPSR I/F capability. Add narrow family APIs where useful; do not create a parallel synchronization abstraction.
All link_section, addr_of_mut!, and raw pointers should be banned outside dtcm/. Too broad. Entry points, packet-RAM reservations, exception state, PHY buffers, and diagnostics legitimately use those forms. Gates must target direct DTCM address construction and .dtcm.* ownership, not syntax unrelated to DTCM.
The DTCM file should become independently anchored family objects. Contradicts the native-layout plan. Split source organization only; preserve one physical quarantine allocation until whole closures retire.
DTCM usage was properly translated because its physical map and pointer audit were complete. False. The geometry is exceptionally well mapped, but initialization, access confinement, writer closure, and native ownership remain incomplete. The main image has no DTCM load segment; several production paths still use literals or raw integer arithmetic.
The HIF output queue was missing. The 64-entry software queue and four descriptor staging slots exist. The remaining question is whether copied confirmations and early request-credit return are the clean contract we want.
Active probe TX and ordinary protected traffic were open. Both work and are hardware validated.
The firmware should be redesigned around a new static-priority task scheduler. No current evidence justifies that rewrite. Preserve the bounded cooperative reactor and make its lanes explicit in code.

5. Target code structure

This is a source decomposition, not a physical memory-layout change. Perform it incrementally, with one behavior-preserving extraction per change.

├── firmware.rs                 cooperative reactor and lane ordering

5.1 Dependency rules worth enforcing

  • Only dtcm/ may construct a DtcmAddress from a numeric address or expose a fixed-DTCM linker member. Other modules receive typed field addresses.
  • Only packet_ram.rs may allocate packet-RAM regions; users operate through owning tokens or checked addresses.
  • Only the holder of MacDomainGuard may execute documented compound MAC-state transitions.
  • Only one MacEventQueue capability exists and all consumers borrow it.
  • Pure decision/build functions do not read MMIO, DTCM, clocks, or global diagnostics.
  • Diagnostics never participate in correctness and normal feature-free builds retain no verbose trace cost.

6. Phased implementation plan

PhaseWorkExit criteria
P0 source truth Keep README current-state and open-item lists authoritative. Add explicit "historical" notes to stale implementation-delta sections when touched. Record source precedence from section 2 and preserve the qualified traffic baseline. No current backlog item is derived solely from a superseded experiment section; the exact qualified image and hardware protocol remain reproducible.
P1 DTCM runtime contract Build a live-field matrix for every production DTCM consumer: physical field, semantic owner, initializer, cold-boot source, warm-reload behavior, readers, writers, required exclusion, and whether it is hardware-visible. Replace direct production literals and manual offsets with existing field-derived accessors. Add a DTCM-specific literal/access gate. Only after that audit, split dtcm.rs into source modules while preserving the one physical DtcmLayout. Every live field has a deterministic initialization/retention contract; cold and warm snapshots match that contract; no unexplained production DTCM literal remains; DTCM sizes, offsets, linked addresses, initialized bytes, and interval gates remain exact. This phase moves no address.
P2 reactor extraction Extract WSM command dispatch from the 1,020-line binary. Introduce a Firmware state owner whose methods correspond to the existing service lanes. Preserve exact lane order and bounded work. Host tests and check.sh pass; target image qualifies under the existing three-boot TCP/UDP/ping protocol. No new state machine.
P3 TX decomposition Split tx.rs and vendor_host_tx.rs at the boundaries in section 5. Move pure builders and decisions first, then target executors. Make the arena model share transition predicates with runtime decisions instead of duplicating them. No increase in unsafe call sites; existing focused tests move with each unit; production qualification remains healthy. The ELF identity oracle is used only for slices that promise exact code generation, not as a universal refactor requirement.
P4 correctness and security Add CCMP replay protection with per-key/per-TID receive packet numbers. Make RESET semantics explicit: either support targeted per-VIF epochs as the ownership design specifies, or document and test global reset as the chosen product behavior. Complete active-VIF channel restoration and power-save resume. Replay is rejected without corrupting RX ownership; reset drains every affected owner exactly once; repeated sleep/wake/join/traffic cycles pass.
P5 HIF publication contract Decide and formalize the clean publication contract before adding hardware TX concurrency. Exact vendor same-buffer lifetime is optional. Required properties are atomic ownership transfer, bounded memory, command priority, pressure safety, explicit credit ordering, and release only after the chosen backing storage is no longer hardware-visible. Queue saturation and reordered-completion tests cannot lose a command response, confirmation, request credit, RX token, or shared output slot. The contract is expressed by owning types rather than comments alone.
P6 recovery and soak Classify failures as recoverable, interface-reset, firmware-reset, or terminal. Preserve the qualified corrupt-head normalization and zero-copy resync rules. Define behavior for CPU exceptions and unrecoverable packet-controller faults. Add controlled degraded-RF fallback and long-duration cold/warm qualification. Fault injection and soak runs prove no request token, RX token, pipe slot, or hardware-owned context is released twice or silently abandoned.
P7 safe TX concurrency After the single-owner and HIF contracts remain stable, allow more than one hardware-owned frame with explicit per-pipe credits and identities. Start with two ordinary frames only if pipe/slot ownership and completion routing are proven. Do not add a software FIFO above HostTxDriver. Higher delivered TCP throughput without increased loss, exceptions, leaked credits, unmatched statuses, or watchdog recoveries. Interleave exact-parent control runs.
P8 aggregation Implement A-MPDU construction and BA accounting on top of proven multi-owner pipe credits. Keep host-selected retry policy and current rate-feedback format. Aggregation improves delivered throughput under controlled peers; retry/give-up, teardown, RESET, and power-save paths remain ownership-clean.
P9 DTCM retirement Translate complete scheduler/timer, TX, VIF/PAS/link/BA/power-save, scan/channel, HIF/MIC, and PHY closures while preserving fixed addresses. Then remove remaining roots and loader assumptions in one atomic migration. No fixed DTCM readers/writers/callbacks remain; generated source, linked-image, computed-root, pointer-value, callback, section, stack, and warm-reload gates pass.

7. Performance plan

The qualified firmware is already useful, but the same-board vendor baseline reached 7.3–15.9 Mbit/s TCP. Performance work must be hypothesis-driven and must preserve ownership proofs.

  1. Re-establish a current controlled baseline after the architecture refactors: three fresh boots, TCP, UDP delivered/loss, final ping, TX failures, watchdog recoveries, exceptions, used HIF buffers, pending contexts, and completion drain.
  2. Measure the serialized cycle. Existing comments report roughly 8.4 ms from publication to confirmation and show that raising the software service budget was neutral. Do not mistake queue latency for executor throughput.
  3. Add per-pipe concurrency before A-MPDU. This tests whether the single hardware owner is the main limit while keeping each frame independently confirmable.
  4. Add A-MPDU only on the proven ownership layer. Aggregation must not obscure context, frame-node, pipe, and slot identity or weaken RESET and retry semantics.
  5. Compare vendor initialization only when a measured fault points there. The historical packet-DMA/ring-order investigation remains useful evidence, but it is not the first step for every throughput gap.

8. Validation gates

8.1 Software gates

  • Default and diagnostic-feature host tests.
  • All interval/layout/reference-map checkers.
  • Thumb release build, stack-depth/call-chain checks, sectioned image checks, and packed-image construction.
  • Property tests for ownership transitions, completion reordering, queue wrap, RESET, and saturation. Kani or exhaustive reduced-state tests remain optional if they provide useful coverage.
  • Hardware-AES known-answer matrix, corrupted-MIC rejection, and host RustCrypto equivalence.

8.2 Hardware qualification

  • Interleave parent/control and candidate images when behavior changes.
  • Use repeated cold boots, not one clean run.
  • Verify scan, JOIN, WPA2, DHCP, ping, TCP, UDP, RESET, channel restore, and sleep/wake as the implemented surface grows.
  • End every run with zero leaked request credits, zero pending reversible contexts, no stale hardware owner, and no outstanding RX token except intentional host ownership.
  • Retain external evidence such as driver counters and monitor capture where firmware diagnostics would perturb timing.

ELF identity scope: cec5f4be… and 711c7b98… are exact self-regression baselines for structural DTCM slices and refactors that explicitly promise identical code generation. They are not vendor-equivalence oracles and must not block intentional behavior changes.

9. Non-goals and rejected directions

  • No faithful reimplementation of every vendor subsystem merely because it was decoded.
  • No new RTOS or priority scheduler without a measured defect that the cooperative reactor cannot solve.
  • No movable all-Rust DTCM layout before complete writer closure.
  • No independently anchored DTCM family statics during the quarantine phase.
  • No generation-counter-dependent release correctness. Debug generations are acceptable only as host-test diagnostics.
  • No FIFO above the retained host-TX owner and no command-lane dependency on data completion.
  • No broad syntax bans that prohibit legitimate MMIO, packet-RAM, entrypoint, exception, or diagnostic code.
  • No hardware recovery that reclaims an owner whose device completion status is unknown.
