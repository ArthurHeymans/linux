XR819 open firmware — throughput-improvement plan

Vendor TX transaction reconstruction (publication → MAC status → BlockAck → per-member completion → re-publication) compared with the Rust implementation, with a ranked, staged, falsifiable roadmap. Sources are local only: vendor decompilation/disassembly (Ghidra project xr819-annotated-main / ghidra-fw-main.bin), Ghidra memory reads, and the Rust sources under xr819-firmware/src. 1. Executive summary

  1. The vendor TX completion pipeline is one synchronous interrupt/task hop; the open firmware's is a multi-millisecond cooperative loop with two independent lanes. In vendor firmware the MAC event FIFO is drained by mac_irq_handler (0x9eb4, FIQ). The done event (0x37, class 0x30000) and the status event (0x39) are consumed in FIFO order; the status handler txp_pipe_tx_status (0x9a32) calls txp_fn_2441 (0x91ec), which pulls the compressed BlockAck out of RX packet RAM with rxfifo_find_frame_by_subtype(0x94) (0x8d80) and dispositions every member with bab_process_ba_bitmap (0x7b72) before the handler returns. Only then is event 0x200000 raised, whose task (task_b88e, 0xb88e) re-runs txp_scheduler_run (0xaa5e) and issues the next GO. Confirmed The open firmware instead consumes the BA on the RX lane (radio.rs:1109 → tx::consume_depth_two_block_ack), stubs the pull path (SingleProbeMacBackend::find_rx_frame_by_subtype returns None, tx.rs:3964), and acts on partial observations only from a hardware retry event or after the 5×200 ms pipe watchdog. That lane split is the root of both the recorded ownership race (image a7d56f2a…, BH fatal with 10 outstanding) and the ≈0.6–1 s partial-BA retry latency. Confirmed
  2. Vendor never gives an aggregate up after two attempts. Whole-aggregate retry (txp_pipe_tx_done_retry, 0x9550) bumps every member's per-rate 4-bit nibble and walks the host retry-policy ladder (pas_tx_retry_advance, 0x8868) up to the policy short/long limit; on a rate fallback it copies the head rate to every member (txp_desc_set_rate loop) instead of requiring a common next rate. Partial BAs release acknowledged members immediately and requeue missing members into the global PAS ring (link states 8→9), where the next scheduler pass may re-aggregate them with fresh frames. Confirmed The open firmware has WHOLE_AMPDU_RETRY_LIMIT = 2 (tx.rs:4160), gives up on any member-rate divergence (prepare_whole_ampdu_retry), on outside-window members, on watchdog expiry (retire_unmatched_tx_slot → status 0x0b for the whole slot), and on any partial deeper observation that the selective tail cannot express. Each of those becomes a host-visible failed confirmation, i.e. packet loss for TCP. Confirmed This is the most likely reason "vendor reports thousands of retries while open reports almost none despite failures" and why adaptive minstrel pins to MCS0 (loss at MCS≥1 is reported as failure, not as retries followed by success). Strong inference
  3. UDP "parity" is not PHY parity. The harness offers UDP at 8 Mbit/s (tools/ota-soak-udp-run.sh:143, iperf -u -b 8M); vendor delivers 6.34 and open 6.32. Both are below the offer and equal, which indicates a path/harness ceiling near 6.3 Mbit/s, not that the open pipeline reaches vendor capacity. Strong inference TCP (15.8 vs 2.1–2.65) is the only measurement that currently exercises the firmware's real completion/retry latency, because TCP throughput scales as MSS/(RTT·√loss) and is ACK-clocked. Strong inference
  4. Near-zero host TX burst is a confirm-return artifact, not missing slot chaining. cw1200_bh counts a burst only when more than one credit is free at write time (bh.c:685,528). Vendor coalesces confirms into WSM 0x041e (tx_confirm_build_and_send, 0xb3dc; driver enables it at main.c:674), so credits return in groups. The open main loop publishes at most one confirmation per pass (bin/hif_startup.rs), so credits trickle back one at a time and the host writes one frame per wake. Confirmed (mechanism) / Strong inference (that it explains the counter).
  5. Ranked plan. (1) Pull the BA at MAC status/retry time under a per-slot transaction generation, demoting the RX lane to a record-only mailbox; (2) policy-driven retry budget and vendor head-rate copy, then vendor requeue of missing members; (3) event-driven publication/confirmation with multi-TX-confirm; (4) TALA-style depth scaling bounded by TXOP airtime and the BA window; (5) rate-feedback fidelity checks. Every stage is feature-gated, has a telemetry gate, and an explicit abort/rollback condition, because stack headroom is 52 bytes (deepest chain 6860 of 6912) and ITCM is at its limit.

4. Disassembly findings

4.1 Q1 — Vendor TX transaction from publication to next publication

Addresses are Ghidra addresses in ghidra-fw-main.bin; DTCM literals were read with ghidra memory read. Pipe records live at 0x04001680 + pipe*0x6c (DAT_0000ab0c), the software slot ring at pipe+0xa0 with 0x18-byte slots; the MAC pipe register block is 0x09c00e80 (DAT_000098d0) with +0x04 = command/pending mask (written inverted) and +0x18 = trigger/clear (1<<pipe)<<25; the same register is reached as 0x09c00e40+0x58 in the scheduler. The Rust constants agree: PIPE_IRQ_PENDING = mac_register(0x0e84), PIPE_IRQ_TRIGGER = mac_register(0x0e98) (tx.rs:145-146). Confirmed

Step C — descriptor build (txp_build_pipe_descriptor 0xa712)

Kind 1 pops a software record (desc_freelist_pop), emits opcode-0 transfers for each member, opcode-1 delimiter + opcode-4 spacing between members, opcode-2 terminal, then the three shared PHY words (opcodes 3,3,5) at the top-level command, sets slot expected status +0xd = 0x0c and special-ack +0xe = 1 only if no member has flags bits 20/21, and advances the producer modulo 4 (pipe_tbl[1] = old; *idx = (old+1)&3). Confirmed The open builder reproduces this stream (tx::build_planned_ampdu_descriptor, qualified on air).

4.2 Q2 — How vendor avoids status/BA races

  • Single writer in FIFO order. All slot-state transitions (1→2→3→{4|5}) and the BA pull happen inside mac_irq_handler in event order. The RX handler never touches TX slot state; it only writes link state 7 ("blocked") in rx_handler. Confirmed
  • Slot state byte as the guard. txp_pipe_tx_status and txp_pipe_tx_done_retry both require state==3; whichever event arrives first wins and moves the slot to 5 or 4, making the other a no-op. Confirmed
  • Retry-busy byte (pipe_table+7, Rust LOW_MAC_PIPE_BUSY): set on retry entry, cleared on the next done event; a status arriving while a retry is being programmed is suppressed after the slot mark. Confirmed
  • Mismatch counter (0x04001f8c+pipe): three consecutive unexpected statuses on an armed pipe force the retry path, bounding a stale expected byte. Confirmed
  • Link state as a generation. The link byte (state 10 = "completed, BA pending", 8 = "requeue pending", 9 = "requeued", 11 = "no BA") gates the aggregate builder (txq_try_append_to_aggregate refuses 6,7,8,10), so no new aggregate for that link can be built while a previous one's members are undispositioned. This is the vendor's transaction epoch: there is at most one outstanding aggregate per link. Confirmed
  • Deferred BA scan cursor. rxfifo_find_frame_by_subtype uses its own cursor (0x040016c0) that advances only across non-BA slots, so a BA that arrives late is found by the next completion on that pipe (the "not last slot → stay in state 10" rule). Confirmed
  • No timer or epoch counter is involved; the 200 ms watchdog (FUN_00003bac) is only a recovery path that aborts the pipe (txp_fn_4155 0x101f4). Confirmed

4.3 Q3 — Are acknowledged members released before missing-member ownership is safe?

Yes. Ownership is transferred in three steps that never overlap: (1) txp_pipe_tx_status recycles the pipe slot (cursor advance or armed=0) and pushes the software record back to the free list, so the hardware no longer references any member; (2) bab_process_ba_bitmap completes acknowledged members with tx_ctx_free_locked and marks missing ones 0xfe with flag 0x10000010, leaving them only in the per-link 16-entry table (0x04001b10 + link*0x40); (3) the next scheduler pass compacts that table and pushes the survivors onto the global ring with the retry bit set in their sequence-control descriptor words. The retried member thus becomes an ordinary ring entry again (possibly re-aggregated with new frames, since bits 20/21 stay clear and state 9 permits appending). The open firmware's selective path instead keeps the slot in state 4 and rewrites the descriptor in place, which is why it needs the "never a second GO" and command-mask release rules and why the acknowledged member's completion had to be threaded through partial_give_up/enqueue_acknowledged_aggregate_member. Confirmed

4.4 Q4 — How vendor keeps the MAC busy; the near-zero TX burst

  • Up to four pipes armed concurrently, one transaction each; ordinary pipes carry up to four slots per GO, aggregate pipes one kind-1 slot with up to 16 MPDUs. Confirmed
  • Every completion (txp_fn_2441, bab_process_ba_bitmap, task_22bc) raises event 0x200000, registered at init to task_b88e (sched_register_task(0x200000, 0x0000b88f), Thumb). That task walks the pending list and ends with txp_scheduler_run(). Re-arm latency is one scheduler hop, not a polling interval. Confirmed
  • The scheduler also runs from phy_resume_state4 and the PS-dequeue task; the MAC-idle event (0x80000000) has its own task. Confirmed
  • Confirms are batched: tx_confirm_build_and_send builds 0x041e with a u32 count and 32-byte entries; hif_confirm_coalesce_hold holds the flush while ring depths are ≤ thresholds (10/4/2) for at most 8000 ticks. Credits therefore return to the host in bursts. Confirmed
  • Open firmware's near-zero TX burst. tx_burst = input_buffers − hw_bufs_used is evaluated per BH TX; the counter increments only if >1 after a write (bh.c:685,528). With one confirm per main-loop pass and the firmware holding ≈30 buffers under load, at most one credit is free at any write. The cure is not slot chaining (vendor has none either) but faster/batched credit return and shorter firmware queueing. Strong inference — falsified if MULTI TXed and TX burst stay near zero after Stage 3.
  • Dead air per transaction in the open loop is ≈ one pass. The main-loop comment records ≈5 ms/pass under load with older code (bin/hif_startup.rs:414-420); the depth-4 image's extra +1.9 ms ping over depth-2 matches one added scheduler_single_wait pass, suggesting ≈2 ms today. At MCS1 a 4×1500-byte aggregate is ≈3.7 ms of air, so a 2–5 ms gap alone caps duty cycle near 45–65%. Strong inference

6. Why UDP can match while TCP stays far behind

  1. The UDP figure is ceiling-limited by the harness, not by the firmware. Offered 8 Mbit/s, delivered 6.34 (vendor) and 6.32 (open) — identical to within noise and both ≈21% below the offer. A firmware capable of 15.8 Mbit/s TCP does not drop 21% of a 8 Mbit/s UDP stream unless something else in the path (AP/uplink/iperf2 pacing in the netns) drops it. So "UDP parity" bounds the open pipeline from below (≥540 frames/s) and says nothing about the top. Strong inference Falsification: offer 20 Mbit/s UDP to vendor; if it delivers ≫6.3, the ceiling was the test.
  2. TCP is loss- and RTT-sensitive; UDP is neither. Every open-firmware give-up (§4.6) is a lost segment. With ≈650 non-unanimous depth-3/4 aggregates in 20,161 frames and only 17 selective retries, even a few-percent give-up rate combined with a queueing RTT inflated by ≈30 buffered frames (≈45 KB, ≈150 ms at 2.5 Mbit/s) yields the observed 2–2.6 Mbit/s via the MSS/(RTT·√p) relation. UDP simply records the loss. Strong inference
  3. Partial-BA stalls are RTO events. A deferred retry waits for the 200 ms watchdog to count down from 5 (Expired at 0 after Nudge at 1–2), i.e. 0.6–1.0 s during which the AC pipe is owned and nothing else on it transmits. TCP's RTO fires, cwnd collapses to 1 and slow start restarts; UDP just delays. Confirmed (mechanism) — the fraction of the 17 selective retries taken via the watchdog vs the retry event is not yet counted (Stage 0).
  4. Bidirectional coupling. TCP needs ACKs on RX; the open RX lane, MAC lane and HIF all share the ≈2–5 ms pass, so ACK delivery and confirm delivery are quantised to the pass. Ping averages (+1.6 ms depth-2, +3.5 ms depth-4 over vendor) are the unloaded signature of that quantisation. Strong inference
  5. Credit trickle. One confirm per pass keeps the host at ≤1 free credit, so the host BH performs one SDIO write per wake, adding host-side latency per frame; vendor returns credits in coalesced groups. Strong inference

8. Staged implementation roadmap

All stages are feature-gated, land one at a time, and are qualified against the WPA2 HT AP with the OTA harness; recovery firmware is restored after every run. Each stage lists its Rust change areas, host tests, telemetry, success criteria, and abort conditions. Stack (tools/check-rust-main-stack.py) and ITCM size are gates for every stage.

Stage 0 — Telemetry only (no behaviour change)

  • Rust: host_tx_diagnostics.rs (new saturating counters in the existing reused-MIB words; extend tools/decode-ampdu-depth-telemetry.py), hooks in tx.rs: decide_retry, complete_give_up, service_expired_partial_block_ack_retry, retire_unmatched_tx_slot, consume_depth_two_block_ack; loop-pass counter and confirms-per-pass histogram in bin/hif_startup.rs.
  • Counters: aggregate outcome = {all-ack@status, all-ack@retry, partial@retry, whole-rearm, give-up:limit, give-up:rate-divergence, give-up:outside-window, give-up:watchdog, give-up:plan}; BA-observation-to-rearm latency buckets {same pass, <10 ms, <200 ms, ≥600 ms}; main-loop passes/s; confirms per pass; max PAS ring occupancy; expired-lifetime count.
  • Host: capture cw1200 debugfs TX failed, MULTI TXed, TX burst, AGG TXed before/after each phase (post-traffic only, per harness note).
  • Success: counters decode; sum of outcomes equals published aggregates. Abort: any change in TCP/UDP beyond run-to-run noise (telemetry must be free).

Stage 1 — Retry budget parity (gate: experimental-depth-four-ampdu)

  • Rust: tx.rs prepare_whole_ampdu_retry: replace WHOLE_AMPDU_RETRY_LIMIT with rate_policy::retry_step per member (limit = policy short/long retries, already implemented for kind 0); on rate change write the head's next rate to every member (vendor 0x9550 loop) instead of returning None on divergence; keep outside-window → give-up until Stage 4. rate_policy.rs: no change. Tests: host unit tests for "member with higher try count follows head rate", "policy exhaustion gives up exactly once".
  • Telemetry gate: give-up:limit and give-up:rate-divergence → ≈0; whole-rearm count rises; host TX failed/1,000 confirms drops toward vendor.
  • Success: fixed-MCS3 TCP ≥ 4 Mbit/s and adaptive no longer pinned at MCS0 (bitrate ≥ MCS2 after 30 s). Abort: BH TX-confirm timeout, buffers not drained, or stack check fails.

Stage 2 — BA join at MAC-event time with generation (gate: experimental-ba-join, new)

  • Rust: tx.rs: implement SingleProbeMacBackend::find_rx_frame_by_subtype using RxFifoStateAddress::ba_scan_cursor() (0x040016c0) and the existing read-only cursor helpers against producer 0x09c00604 (exact vendor walk: rxfifo_off_to_addr, rxfifo_advance(+0x2f, mask), rxfifo_slot_valid); add Transaction.gen to the per-(pipe,slot) retained state (depth_two_block_ack array becomes BaMailbox keyed by link with gen); in service_txp_pipe_tx_status for kind 1 call the join before complete_tx_pipe_slot and disposition members (Confirm/Retry) instead of confirming all; in decide_retry perform the same join before choosing whole rearm. radio.rs:1109: consume_depth_two_block_ack becomes record-only (write mailbox, never PIPE_IRQ_TRIGGER/complete_tx_pipe_slot). Remove the watchdog retry trigger (service_expired_partial_block_ack_retry) once the join is qualified; keep watchdog recovery.
  • Tests: host tests for the generation invariant (stale mailbox ignored; mailbox from the same generation consumed once), for the "not last slot → defer" rule, and for join ordering (status before RX, RX before status, retry event with all-ack).
  • Telemetry gate: BA latency bucket ≥600 ms → 0; partial@retry and partial@status both non-zero; zero refused statuses on armed pipes (STATUS_INELIGIBLE unchanged).
  • Success: depth-4 TCP ≥ depth-2 TCP (today it is lower), no BH fatal in 3 consecutive 60 s soaks, 20/20 ping. Abort: any TX-confirm timeout with outstanding frames (the signature of image a7d56f2a…); then keep the mailbox but re-enable watchdog-only action.

Stage 3 — Event-driven service and batched confirmation (gate: experimental-fast-loop)

  • Rust: bin/hif_startup.rs: drain up to N (start 4) confirmations per pass; skip the one-pass fill wait when the target pipe is idle and no owner exists (host_tx_driver.rs publish_ready_batch); wsm.rs: add 0x041e encoder (u32 count, 32-byte entries, len 0x28 + 0x20·(n−1)); hif.rs: publish one coalesced message per pass using one request buffer; return credits for all n. Measure pass cost with the existing iteration counter and, if the timer read is affordable at 1/16 passes, a pass-duration histogram.
  • Tests: encoder layout test against wsm_multi_tx_confirm parsing (count, per-entry offsets), confirmation-order preservation.
  • Telemetry gate: host MULTI TXed > 0, TX burst > 0; passes/s up; ping avg within 1 ms of vendor.
  • Success: fixed-MCS1 TCP ≥ 3.5 Mbit/s (vendor 4.14). Abort: host WSM sequence errors, any credit accounting mismatch (hw_bufs_used negative warning), or output-descriptor starvation of the command lane.

Stage 4 — Vendor requeue of missing members (gate: experimental-member-requeue)

  • Rust: tx.rs: on partial join, complete acknowledged members, retire the kind-1 slot, and hand missing members to a new per-link "requeue pending" set (mirror of 0x04001b10 table + link state 8); vendor_host_tx.rs: reuse the exact PAS-ring compaction/insertion model to push them back with flags |0x10, retry bit 0x800 in sequence-control words, bits 28/5 cleared; host_tx_driver.rs: allow Scheduled → PasQueued for those contexts (retaining packet id, try count, nibbles) and let plan_ampdu_group re-aggregate them (vendor permits when bits 20/21 are clear). Outside-window members follow the same path (vendor behaviour) instead of give-up. Delete the in-place selective tail for depth>2 once qualified (stack relief).
  • Tests: ring compaction with mixed fresh/requeued entries, exactly-once completion of acknowledged members, RESET while members are in the requeue set.
  • Success: selective retry counters replaced by requeue counters; give-up:plan → 0; deepest stack chain shrinks. Abort: duplicate confirmations (host warns unknown packet id) or retained buffers after drain.

Stage 5 — Depth scaling (gate: experimental-depth-eight-ampdu)

  • Rust: host_tx_policy.rs: MAX_EXPERIMENTAL_AMPDU_DEPTH 4→8 with a per-link cap input; BA-window bound (seq < min_seq + 64); EDCA TXOP airtime from configuration.rs (the WSM 0x0013 values already parsed) as the airtime budget; TALA-like adaptation (halve on >25% member failure per 400 completions, +1 after 5 clean windows, floor 2). tx.rs: member arrays sized by the new constant; copied-completion queue 16→32 only under the gate; flight recorder reduced as before to fit ITCM. Later 8→16 only after Stage 4 removes the in-place selective tail.
  • Success: fixed-MCS3 TCP ≥ 6 Mbit/s, MCS5 ≥ 8; no increase in give-ups. Abort: stack check < 0 headroom, ITCM overflow, or first-member-loss regressions.

Stage 6 — Rate feedback (driver + firmware)

  • Verify nibble content of retried members after Stage 4 (member carries its own try count); evaluate setting IEEE80211_TX_STAT_AMPDU with ampdu_len = 1, ampdu_ack_len = ACK?1:0 (semantically what mac80211 does anyway) or, better, batching per-aggregate status; compare minstrel_ht rate tables (rc_stats) vendor vs open at the same RSSI.

10. Risks

  • Stack/ITCM. 52 bytes headroom in the depth-four feature build; the join in Stage 2 adds a scan loop on the status path (small), Stage 4 removes the deepest chain (in-place rebuild). Order Stage 4 before Stage 5. Mitigation: #[inline(never)] on the join, no new arrays on the status path, stack check in CI for every gate combination.
  • BA scan cursor semantics. The vendor cursor advances across non-BA slots and can lag; earlier open experiments that coupled it to release policy found nothing because the RX filter was wrong at the time. With the corrected filter the BA is in normal RX packet RAM; a stale or wrapped cursor is the main residual failure mode. Mitigation: bound the scan to one FIFO length, validate with rxfifo_slot_valid, fall back to the mailbox.
  • Double consumption of a BA. The RX lane currently releases the BA slot; if the MAC lane pulls it from packet RAM in the same pass the slot may already be released. The generation-tagged mailbox makes the pull optional whenever the RX lane already observed the frame for the same generation.
  • Requeued members and sequence order. Re-aggregating a retried member with newer frames is what vendor does, but the receiver's BA window must still cover it; keep the BA-window bound in the planner.
  • Multi-confirm and HIF credit accounting. The host releases count−1 extra credits on 0x041e; the firmware must return exactly one request buffer per confirm regardless of coalescing.
  • Debugfs during traffic destroys the open firmware (harness note); all telemetry must be post-traffic.
  • Transient post-traffic ping loss is documented and should not be treated as a firmware regression unless buffers remain owned.

11. Unanswered questions

  1. Does the MAC deliver 0x0c only for an all-acknowledged BA, raising 0x19/4 otherwise? The forced-duplicate test (both MPDUs seq N) produced matching statuses, consistent with the hypothesis, but the open path also saw "all-ack retry events". Stage 0's partial@status vs partial@retry counters answer this.
  2. What writes DTCM 0x04001160 (the vendor state-11 "retry allowed" word; only reader 0xa404)? The vendor container image shows a nonzero initial value at the mapped offset if the DTCM mapping in data/README.md holds. Not needed for the plan.
  3. Exact current main-loop pass cost and its distribution; the only measurement (≈5 ms) predates several changes.
  4. Why the harness UDP ceiling sits at ≈6.3 Mbit/s for both firmwares (AP uplink, netns pacing, or iperf2 −b implementation).
  5. Vendor initial vif+0x128 (ampdu_num) value before TALA adapts it; the driver never sends MIB 0x000A/0x000B.
  6. Whether minstrel_ht's sample-rate frames are routed as singletons by vendor as well (rate mismatch closes the aggregate in both), and how much airtime they cost at high depth.
  7. Whether the AP's BA reorder window tolerates the vendor-style re-aggregation of a retried member behind newer sequences at depth 16 (it must per 802.11, but the specific AP has not been tested).

12. Three recommended next experiments (with falsification criteria)

E1 — Outcome and latency census (Stage 0)

Build the depth-four diagnostics image with the outcome/latency counters; run the standard WPA2 sequence at fixed MCS3 and adaptive; read the counters and host debugfs post-traffic; repeat on vendor for the host counters.

Predicts: give-up outcomes ≥ 5% of non-unanimous aggregates; ≥600 ms latency bucket non-zero; host TX failed per 1,000 confirms ≥ 10× vendor; open MULTI TXed = 0.

Falsified if: give-ups < 1% and the ≥600 ms bucket is empty — then the TCP gap is dominated by loop latency (go to E3 first), not loss.

E2 — Retry-budget parity (Stage 1)

Replace the two-attempt limit with the policy ladder and copy the head rate to members; same runs as E1.

Predicts: host TX failed drops by ≥ 5×, whole-rearm count rises, adaptive bitrate leaves MCS0 within 30 s, fixed-MCS3 TCP ≥ 4 Mbit/s.

Falsified if: TCP does not improve by ≥ 25% while failures drop — then loss was not the binding constraint and Stage 2/3 latency work must lead.

E3 — De-alias the UDP ceiling and the pass cost

Run vendor and open with UDP offered at 20 Mbit/s (and 8 Mbit/s as control); log the main-loop iteration counter delta over each 20 s phase (already supported) to derive passes/s; optionally sample the timer 1/16 passes for a duration histogram.

Predicts: vendor delivers ≥ 10 Mbit/s at 20 M offered while open stays ≈6 Mbit/s; open passes/s ≈ 200–500 under load and confirms/pass ≈ 1.

Falsified if: vendor also caps at ≈6.3 — then the harness path, not firmware, sets the UDP ceiling and UDP must be measured on another server; or if passes/s ≫ 1,000 — then loop latency is not the dead-air source and the burst counter must be explained by credit accounting alone.
